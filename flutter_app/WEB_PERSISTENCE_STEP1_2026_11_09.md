# Notes Web — Step 1: persistent browser workspace (2026-11-09)

## Scope / exact boundary

This step replaces the **in-memory-only** note/collection/automation state of
`flutter_app/lib/web_preview.dart` with a small, local browser workspace.
The existing Dart `Note` (including canonical TaskDetails/Sketch/Whiteboard
JSON fields) and `WorkflowRule` models are serialized. No extra Notes data
model, remote service, account, new Android database, APK, or AI dependency.

The Web entry point is still `lib/web_preview.dart`, NOT the Android entry
point. A Web deployment is not a claim of native or Play certification.

## Mechanism

- `WebWorkspaceStore` uses **existing shared_preferences Web** which stores
  data in browser localStorage, scoped to this origin/profile.
- Two alternating versioned slots, whole-snapshot SHA-256 verification,
  monotonically increasing sequence; a partially corrupt newest slot can fall
  back to the last acknowledged good snapshot. If none is readable, fail closed
  instead of silently reseeding and overwriting the user's browser content.
- Writes are queued; canonical UI state changes **only after successful
  persistence and readback**. A failed save leaves the last UI snapshot intact
  and displays an error. Refresh reloads the latest verified journal.
- Initially **empty workspace**; no autogenerated demo notes, tasks, Trash
  records or collections. Previously only ephemeral seed content existed.
- Notes, tasks, checklists, diary entries, collection changes, annotations
  inside Note's visual document JSON, Trash/restore/purge, and automation
  flags/receipts are covered by snapshot writes.
- Manual **copy JSON export / paste JSON import** in Settings with manifest,
  schema, SHA-256, strict ID validation, preflight, counts and confirmation
  before replacing the current browser workspace. Clipboard content is
  sensitive; store exported data privately.

## Limits / truthful product labels

This is a **text-first bounded localStorage implementation**, not IndexedDB,
SQLite/WASM, or multi-device sync. Conservative limit: 750,000 UTF-8 bytes per
snapshot; localStorage browser quotas can be lower and can vary. Large media,
native scanner/OCR, real Shared Spaces sync, full Project data, remote GitHub
sync and complete Study persistence are **not implemented on Web by this step**.
Some advanced Web surfaces remain projections/functional previews, so the UI
must not imply cloud or Android integration. Clearing site storage, private
browsing expiration, user profile changes or browser cleanup can erase local
content: users must export a separate recovery copy.

No external storage or telemetry is added. No SDK, key or billing workflow is
altered. Background sync and file download are not introduced. A subsequent
scale increment can replace only the Web storage adapter with IndexedDB or a
WASM database while preserving the versioned snapshot contract.

## Validation required

1. Dart formatter, Flutter analyze/tests on exact PR head.
2. Unit tests: empty startup, note/task/sketch/automation round-trip, refresh,
   deletion persistence, newest-slot corruption fallback, both-slots corrupt
   fail-closed, export/import checksum and duplicates, quota failure.
3. Web build with `--target lib/web_preview.dart`; deploy preview (no APK).
4. Browser smoke: create/edit/reload; close and reopen tab; Trash and restore;
   collections and automation toggle; copy export/import into another browser
   profile; tamper with payload and assert no overwrite; clear site storage
   explicitly and observe fresh empty workspace.
5. Verify settings accurately differentiate local persistence from project,
   Study and Android-only integrations.

GitHub Actions green proves the source/build pipeline, not browser-profile
persistence or full product parity. Browser smoke verification is a separate
gate, as is independent Golden certification.

## Step 2 — 11 November 2026: Web journal readback and recovery hardening

- Startup now reloads the browser-backed `SharedPreferences` before reading either journal slot. This reduces stale-cache reads when switching browser tabs; it does **not** implement atomic multi-tab locking.
- Normal commits reload the backing store after `setString`, check the exact encoded receipt and decode its bounded, checksummed sequence before acknowledging the new UI snapshot. A readback failure is surfaced rather than treated as success.
- Confirmed recovery from two corrupt slots similarly verifies the surviving journal and the removal of the bad alternate. JSON parsing rejects oversized local journal strings before decoding.
- Export waits for the existing serialized write queue and refuses to export a placeholder when storage was blocked or unreadable.
- Added unit coverage for startup refresh, oversized corrupt-slot fallback and recovery cleanup. Browser-origin persistence, power loss, cross-tab write races, quota enforcement and external-file backup still require actual browser QA.
- **Limits unchanged:** localStorage 750,000 bytes per encoded snapshot, JSON manual export/import, no IndexedDB, media parity, multi-device sync or atomic cross-tab CAS. SharedPreferences reload + readback cannot guarantee two simultaneously writing tabs are serialized; use one editing tab per browser profile until a transactional store is separately designed.
- This is a bounded repair, **not** certification of the Web workspace or activation of a new product feature. Exact-head `verify-web`, `verify`, `build-web` and browser smoke evidence remain separate gates.
